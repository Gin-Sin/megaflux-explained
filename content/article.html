MegaFlux,
explained.

Move the work. Hide the cost.

One busy expert can leave a cluster waiting. MegaFlux gives that expert more places to run—and overlaps the communication needed to make it happen.

01 / THE PROBLEM

A faster kernel can still wait.

A mixture-of-experts layer finishes at the pace of its busiest GPU. Making each GPU efficient does not make their workloads equal.

In a mixture-of-experts (MoE) layer, a router chooses a small set of feed-forward networks—experts—for each token. With expert parallelism, different GPUs own different experts. A token must travel to a GPU holding its selected expert’s weights, run through that expert, and return for a weighted combination with the other selected experts’ outputs.

Route tokens→Dispatch→Expert compute→Return + combine

A conventional implementation separates communication and computation into GPU kernels. A persistent megakernel keeps worker groups resident and lets them process ready pieces of work: one group moves tokens while another multiplies matrices. Readiness flags connect producers to consumers. MegaMoE already uses this approach; MegaFlux extends it. Metadata routing and the final top-k sum still use separate launches. [§2.1]

Now suppose four GPUs receive 12, 4, 4, and 4 equal-cost blocks of work. The average is six, but GPU 0 must execute twelve. The other GPUs cannot take its extra blocks because they do not hold that expert’s weights. Communication/computation overlap inside each GPU leaves this placement constraint intact.

Routing skew means some experts receive more assignments than others. Skew becomes a GPU straggler when the resulting work concentrates on particular owners. The paper measures real routing profiles and finds 7.3–41.0% higher fixed-placement latency than its balanced-route comparison. That motivates replication, but does not imply that every skewed workload benefits. [§2.2]

Two kinds of imbalance: experts versus GPUs

The paper measures expert skew with \kappa = E\sum_e \left(c_e / \sum_j c_j\right)^2, where c_e counts assignments to expert e. Uniform expert loads give \kappa=1. But runtime depends on the sum of work assigned to each GPU. The same expert-load histogram can produce different GPU loads under different ownership arrangements. MegaFlux’s planner therefore optimizes per-GPU block load.

KEEP THIS IDEA

Fusion improves how assigned work executes. Replication expands where that work can execute.

02 / THE PLACEMENT DECISION

Move blocks. Preserve the model.

MegaFlux changes the GPU that executes an assignment while preserving the router’s expert choices and weights.

A replica holds a copy of an expert’s parameters. If token t selected expert E_0, it still runs E_0—possibly on another GPU. The planner preserves token identities, expert selections, assignment counts, and routing weights. It neither drops inconvenient tokens nor sends them to a less busy, different expert. This preserves the intended model computation, subject to the implementation’s numerical behavior. [§3.1]

Partition first; assign second.

GPU matrix multiplication processes tiles. Splitting an expert’s token count independently across copies can create several partly filled tiles. MegaFlux instead partitions that expert’s routed rows into blocks of at most \beta rows before assigning the blocks to GPUs. An expert has b_e=\left\lceil c_e/\beta\right\rceil blocks, with at most one partial block across all its copies. The main evaluation uses \beta=128.

A SMALL EXAMPLE

300 routed rows become 128 + 128 + 44. Move a complete 128-row block to a replica and keep the remaining blocks on the owner. Only the 44-row block is partial. Splitting into 150 rows per copy would instead produce 128 + 22 on both copies.

The planner chooses q_{er}, the integer number of expert e’s blocks assigned to GPU r. It minimizes the largest GPU load, while conserving every expert’s blocks and limiting the number of remote experts each GPU hosts. A replica consumes one slot whether it receives one block or twenty.

\underset{q\in\mathbb{Z}_{\ge 0}^{E\times P}}{\operatorname{minimize}}\;\max_r\ell_r\ell_r=\sum_e q_{er}
The constraints and the four-candidate heuristic

Every expert keeps all of its blocks:

\sum_r q_{er}=b_e\qquad(\forall e)

Every GPU respects its replica capacity:

\sum_{e:\,h(e)\ne r}\mathbf{1}[q_{er}>0]\le s

Here h(e) is the owner of expert e, and s is the replica budget. Every q_{er} is a nonnegative integer.

The target is \tau=\left\lceil\frac{\sum_e b_e}{P}\right\rceil blocks per GPU. Four warps independently search four candidates: two donor priorities crossed with two fan-out policies. They reuse existing replicas, then open new copies on eligible underloaded GPUs. A transfer moves min(owner’s remaining blocks, receiver’s room below \tau). It is not capped by the donor’s excess, so a donor may become underloaded.

Each search stops after s+2 rounds or a round without movement. The planner selects the smallest maximum load, breaks ties by fewer replicas, then prunes and refines. This is a bounded heuristic, not a guarantee of the mathematical optimum. Finally it builds a block-to-GPU table from a stable ordering of routed assignments. [Appendix A]

THE NEXT CONSTRAINT

A balanced assignment is only a plan. The destination still needs the expert’s weights before it can execute.

03 / FORWARD EXECUTION

A replica can start half ready.

The first projection needs W_1. It can run while the second projection’s W_2 is still in flight.

Each expert applies an input projection (FC1), a SwiGLU activation, and an output projection (FC2). The two weight matrices serve different operations:

Z=XW_1,\qquad A=f(Z)O=AW_2

The router-weighted sum combines the selected experts’ outputs for each token. These equations omit quantization.

A separate-stage replication scheme transfers all replica weights before starting expert computation. MegaFlux gives W_1 and W_2 separate readiness conditions. FC1 starts when W_1 and an input block are ready. FC2 starts when W_2 and that block’s activation are ready. No full-replica barrier needs to sit between communication and useful work. [§3.2]

Weight movement shares the megakernel’s communication workers. A small subset services replica weights from the start. Other input-transfer warps first finish their assigned token blocks, then join the weight-transfer queue. Owned experts can compute while replica weights move. The schedule gains overlap without reserving a completely separate worker group for replication.

What “ready” means at the execution level

A cooperative thread array (CTA) is a GPU thread block. Persistent CTAs contain worker groups with different roles, such as loading operands, moving tokens, performing matrix operations, and writing results. Loaders obey projection-level weight readiness and tile-level activation dependencies. The design uses Blackwell matrix instructions, tensor memory, and Tensor Memory Accelerator operand staging; those mechanisms make the pipeline possible, but the key logical rule is that a consumer waits only for the data it actually needs.

THE FORWARD IDEA

Make readiness specific to the next operation, so unrelated work can continue.

04 / BACKWARD EXECUTION

Bring every partial to the table.

Training adds a second bill: every replica produces parameter gradients that must be accumulated at the expert’s owner.

Backward has two jobs. Data gradients (DGrad) propagate the loss gradient toward the input. Weight gradients (WGrad) accumulate how the expert’s parameters should change. When multiple GPUs process different rows for one expert, each contributes a partial weight gradient for that expert. The owner must combine those contributions.

Follow the backward algebra

For expert e, let D_e[t]=p_{t,e}\,dy_t, the output gradient scaled by that token’s routing weight. Let dZ be the SwiGLU backward result. Ignoring quantization:

Dependencies for one expert
OperationExpressionWhat it needs
Activation gradientdA=DW_2^{\mathsf T}Output gradient, W_2
Input gradientdX=dZW_1^{\mathsf T}SwiGLU backward result, W_1
Output-weight gradientdW_2=A^{\mathsf T}DActivations, output gradients
Input-weight gradientdW_1=X^{\mathsf T}dZInput rows, dZ

Each copy computes these weight-gradient products over its assigned rows. Summing the copies’ partials recovers the full expert gradient in the mathematical computation. [§2.1, Eq. 2]

First, overlap the inputs to backward.

DGrad consumes W_2 before W_1, reversing forward’s weight order. Projection-level readiness lets one transfer overlap with ongoing computation. In the MXFP8 implementation, DGrad and WGrad reduce along different matrix dimensions, so WGrad also needs operands requantized along the token axis. Communication workers perform this preparation during otherwise idle intervals. CTAs transition independently from DGrad to WGrad after retiring their previous accumulator state.

Then, advance the last prerequisite for reduction.

Producing one replica’s gradient early is insufficient. The owner can reduce a particular gradient tile only after all participating GPUs have produced their matching partials. MegaFlux prioritizes replicated experts’ gradient preparation and tile production on every participant. Once the required partials are ready, the owner pulls and accumulates them in FP32 in a fixed order while other tiles continue computing. [§3.2]

In the animation, G_0^{(r)} is GPU r’s contribution to gradient tile 0, and dW_0 is the accumulated tile. The small matrix values only illustrate addition.

Why the training planner dislikes tiny replicas.

A replica’s dW_1 and dW_2 partials have the full parameter dimensions even when it processes few tokens. The added reduction work does not shrink with its token assignment. Load balancing can therefore move computation away from a busy owner while giving that same owner a large gradient-reduction burden.

C_{\lambda}(q)=\max_r\bigl(\ell_r+\lambda n_r\bigr)\lambda=12

Here n_r counts remote copies of experts owned by GPU r. It does not count the replicas GPU r hosts. After load-only search and refinement, a pruning pass uses this proxy to remove small replicas; it may accept worse compute balance to reduce owner-side work. The penalty is a fixed heuristic in block units, not a measured conversion to microseconds. If the pruned plan does not strictly improve the proxy over fixed placement, the planner keeps fixed placement. [Appendix A.2]

The training plan is selected before forward and reused unchanged for backward. Planning is charged once, to forward. Inference omits this reduction-aware pruning pass.

THE BACKWARD IDEA

Overlap depends on when the last required producer finishes. Schedule the participants together.

Four comparisons. Four different claims.

The paper separates the effect of replication, the effect of pipelining, comparison with other systems, and end-to-end prefill.

“Trace-derived” does not mean full-model replay. This grid uses synthetic weights and activations. The authors resize captured expert-load histograms and construct routes that satisfy the token counts and distinct top-k expert constraint. The labels “real-high” and “real-extreme” are percentiles within each source; forward and backward labels need not represent the same \kappa. The native-model motivating experiment and the end-to-end test are separate. [Appendix B.1]

How the main-grid numbers are aggregated

Each (expert count, token count, routing family) configuration has three seeded route realizations. Each realization runs in two fresh processes with five warmups and twenty timed iterations. The authors take median rank-maximum latency, then a median across the six realization/run measurements. Forward adds the separately measured median planner time. The headline summary is a geometric mean of configuration speedups, not an arithmetic average of latency reductions.

2. Same replication plan, separate versus pipelined execution

The ablation fixes replica locations and token-block assignments. The separate-stage variant transfers replica weights before computation and reduces replica gradients afterward. MegaFlux pipelines those operations. This isolates scheduling from the quality of the placement plan.

Pipelining yields up to 13.2% additional forward latency reduction and 26.7% backward reduction relative to separate-stage replication in the ablation. These percentages use a different denominator from the headline speedups; do not add them to 1.45× or 1.28×. The estimated hidden fraction is 56–76% for forward weight transfers and approximately 91–100% for backward replica operations in selected real-high cases. It is a latency-derived estimate, not a direct measure of link utilization. [§4.3, Figures 4–5]

3. Other implementations, under BF16

The prior-art comparison uses a BF16 MegaFlux variant and BF16 baselines, rather than the main grid’s low precision. It reports geometric-mean forward/backward speedups of 2.31×/1.53× over Megatron-Core and 1.74×/2.35× over UltraEP. Both use DeepEP and Transformer Engine grouped matrix multiplication. [§4.4]

Unmodified Mixture-of-Kittens performs additional shared-expert work and, during backward, routing-coefficient gradients. Raw comparisons therefore cover unequal work. The paper adds a serial estimate of that extra work to MegaFlux and reports adjusted speedups of 1.70× forward and 1.26× backward. Treat that adjustment as a comparable-work estimate, with its stated assumptions.

4. End-to-end vLLM prefill

The authors integrate MegaFlux into vLLM 0.27.1 for DeepSeek-V4-Pro-0813 on eight B200 GPUs. They use 160 LongBench-Pro prompts and two replica slots per rank. The measured interval ends when every request in the batch has produced its first output token. These results establish prefill-oriented batch latency gains for that setup, not steady-state decode throughput. [§4.6]

Why a layer gain becomes a smaller application gain

Only part of an application’s time is spent in the accelerated operation. As an illustrative Amdahl calculation, if half the original time were accelerated by 1.45×, the total speedup would be \frac{1}{0.5+0.5/1.45}\approx 1.18. The 50% fraction is invented for explanation; this does not derive the paper’s measured vLLM results.

06 / ENGINEERING JUDGMENT

Balance is necessary. Profit is conditional.

Replication is useful when reduced straggler time exceeds the planning and communication that remain exposed.

The paper gives clear counterexamples to universal gains. Balanced routes have geometric-mean speedups of 0.985× forward and 0.999× backward—near parity, with slight overhead. Some small skewed backward workloads fall to 0.91×. Across one planner experiment, planning itself takes roughly 43–72 μs depending on expert count and workload. Small kernels have less computation over which to amortize that cost. [§4.2] [§4.5]

A REASONING TOOL, NOT THE PAPER’S COST MODEL

Saved straggler time
> planning + exposed weight transfer + exposed gradient reduction

This inequality organizes the implementation decision; the paper does not implement an adaptive profitability gate based on it. The reduction-aware proxy is a narrower heuristic. A runtime gate and topology-aware replication across nodes are explicitly left to future work. Evaluation stays inside one NVLink domain. [§4.6]

Look for

  • Repeated work concentration on a few owner GPUs.
  • Enough expert computation to amortize planning.
  • Spare memory for replica weights and required buffers.
  • Communication that can overlap useful compute.

Measure before adopting

  • End-to-end latency for your actual token regime.
  • The exposed cost of transfers and reductions.
  • Performance on balanced and small workloads.
  • Your interconnect topology and numerical behavior.

Replication itself has a long history in MoE systems. The distinctive contribution here is coupling current-route, block-level placement with the fine-grained dependencies of persistent execution. Forward makes weights available by projection. Backward brings all contributors to a reducible tile earlier. That is the mechanism to carry into your next reading of the paper. [§5]

RECONSTRUCT THE DESIGN

Check your mental model.

Answer each question before opening the explanation.

Why can’t a perfectly overlapped fixed-placement megakernel solve routing skew?

Overlap changes when a GPU moves and computes its assigned work. Fixed placement still forces each expert’s work onto its owner. The overloaded owner remains the straggler even if each of its operations runs efficiently.

A token chose expert E_0. Can the planner send it to E_1 to balance the load?

No. It may send that assignment to another GPU holding an E_0 replica. The selected expert, token identity, and routing weight remain the same.

W_1 has arrived, W_2 has not. What else must be ready before FC1 starts?

The input token block. FC1 needs both its W_1 weights and its input. FC2 later needs W_2 and the activation block produced by FC1.

One replica produces its gradient early. Why might reduction still start late?

The owner needs matching partials from every participating copy. A late producer holds up the tile. Coordinated priority across participants advances the final prerequisite.

Does “99.6% of assignment imbalance removed” mean 99.6% lower latency?

No. It measures the reduction in the busiest GPU’s excess valid assignments above the average, for the specified forward settings. It says nothing directly about transfer, planning, or reduction time. See Appendix B.2. The headline forward layer speedup is 1.45×, which corresponds to about 31% lower latency for a hypothetical case with exactly that speedup—not 99.6%.

KEEP BESIDE THE PAPER

A compact glossary.

Owner
The GPU storing an expert’s original parameters and collecting its replica gradients.
Replica
An additional copy of an expert’s weights on another GPU.
Token–expert assignment
One token’s work for one selected expert. A top-8 token creates eight assignments.
Token block
Up to β routed rows from one expert, assigned together to a GPU.
Persistent kernel
A kernel whose resident workers repeatedly execute scheduled work instead of relaunching for every stage.
Readiness
A dependency condition indicating that an operation’s required data is available.
Exposed overhead
Added cost that remains on the latency-critical path after overlap.
